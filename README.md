# origins-server-resourcepack

Server resource pack for the Cobblemon Origins server (Minecraft 1.21.1).

- `pack/` is the resource pack root. Rank prefix glyphs live in `assets/origins/font/prefixes.json` (U+E200..U+E2FF);
  `assets/minecraft/font/default.json` only holds `reference` providers so each feature keeps its own font file.
- `src/` holds the 1x PNG exports from Figma (`packdev/guipack/figma/04_prefixes.js`); `prefixes.json` maps each
  LuckPerms group to its glyph.
- `python -I build.py` rebuilds `pack/`, runs `check.py` and writes `dist/origins-server-pack.zip` plus its SHA-1.

Each release attaches `origins-server-pack.zip`. The server's `resource-pack` points at
`https://github.com/backyarddd/origins-server-resourcepack/releases/latest/download/origins-server-pack.zip` and
`resource-pack-sha1` must match the release.

## Menus (DeluxeMenus)

Chest-menu backgrounds for DeluxeMenus, drawn in the navy/gold Origins theme.

- `menus/spec.json` is the source of truth: each menu's rows, title, glyph and elements in chest cells (9 columns,
  cell (x, y) = slot y*9+x), plus the DeluxeMenus item (name, lore, click actions) for each clickable element.
- Backgrounds are font glyphs U+E300..U+E3EF in `assets/origins/font/menus.json`; U+E3F0 (-8) and U+E3F1 (-169) shift
  the title so the glyph covers the chest from its top-left corner and the real title text lands at the vanilla x=8.
  Menu titles are `&f<U+E3F0><glyph><U+E3F1>&#fff1d0<Title>`.
- Drawn buttons are invisible `PAPER` items with custom_model_data 7300 (`assets/minecraft/models/item/paper.json` →
  `origins:item/menu_blank`); `slot` elements are transparent holes that show the vanilla slot and real items.
- Figma file `thHX6Yp5pMOLrryrsSaITZ`: page "Menu Kit" (all parts, script `menus/figma/kit.js`) and page "Menus"
  (composed menus, script `menus/figma/menus.js`).

Workflow:
1. Edit `menus/spec.json`, run `python -I menus/build.py validate`.
2. `python -I menus/build.py figma [menu ids]`, then run `menus/figma/out/menus.run.js` with the Figma MCP `use_figma` tool.
   A spec too big for one script is split into `menus.1.run.js`, `menus.2.run.js`, ...; each script redraws only its own
   menus at fixed places, so pass the ids of the menus you changed to get one small script. Other menus' frames on the
   page are never touched (delete a dropped menu's frames by hand).
3. Export each page-level frame `menu_<id>` (download_assets, png, scale 1) to `menus/export/menu_<id>.png`.
4. `python -I menus/build.py build` (validates every export pixel-exactly, writes the glyphs, fonts, item model and
   `menus/deluxemenus/*.yml`), then `python -I build.py` for the zip and SHA-1.
5. Server: copy `menus/deluxemenus/<id>.yml` to `plugins/DeluxeMenus/gui_menus/`, merge `menus/deluxemenus/gui_menus.yml`
   into `plugins/DeluxeMenus/config.yml`, `/dm reload`; publish the pack release and update `resource-pack-sha1`.

### Mod menus

A menu with `"renderer": "mod"` is drawn by the server-side Fabric mod `origins_server` instead of DeluxeMenus. It gets the
same background texture and font glyph, but no `menus/deluxemenus/<id>.yml`, no `gui_menus` entry and no `open_command`;
`[openguimenu]` actions in DeluxeMenus menus and commands cannot target it. Each element `item` is only `{"key": "<key>"}`
(the mod supplies names, lore, materials and clicks) and `dynamic` is not allowed.

`python -I menus/build.py layouts` (also run by `build`) writes `menus/mod/<id>.json` for each mod menu, which the mod reads:
`{"id", "rows", "glyph", "slots": {"<key>": [slot indexes]}}`. Stale files in `menus/mod/` are removed. It needs no exports.

### Warps menu

FTB Essentials has no placeholders for warps, so the warps menu is filled from the server's warp list by
`python -I menus/warps_sync.py` (reads `AFreshWorld/ftbessentials/data.snbt`, writes one page per 21 warps, updates
DeluxeMenus' `gui_menus`, runs `dm reload`; needs the panel API key in `~/Documents/kinetickey`). Run it after every
`/setwarp` or `/delwarp`, and after uploading `menus/deluxemenus/*.yml` (that upload resets `warps.yml` to the empty
base). `--dry-run` prints the pages instead.

### Commands

`commands` in spec.json are command-only DeluxeMenus menus (`/spawn`, `/rules`): an always-false open requirement
runs their actions instead of opening a menu. `register_command` is on, so a new command needs a server restart.

## Cosmetics

Particle effects, tool skin sets, hats, back items, front items and Poke Ball skins for the cosmetics in
`packdev/server/specs/origins-cosmetics/catalog.md` (the source of truth for ids, colours and looks). Everything is
generated by `cosmetics/build.py` from original pixel art drawn in code (`cosmetics/art.py`, drop 2 hats / back / front items and ball skins in `cosmetics/art_drop2.py`, tool sets in
`cosmetics/toolsets.py`); `python -I build.py` regenerates it, runs `cosmetics/check.py` and zips the pack. Generated,
do not edit by hand:

- `assets/origins/bedrock/particles/cosmetics/<id>.particle.json`: one Snowstorm effect per aura, sendout, victory and
  trail cosmetic, identifier `origins:cosmetics/<id>`. Auras loop (`emitter_lifetime_looping`, `active_time` 1, and
  `cobblemon:emitter_space` scaling `entity`); the rest are one-shot bursts. `cosmetics/parts/` holds two helper
  effects (lightning bolt, champion's crown) spawned by their parent's `creation_event`; they are not cosmetics.
- `assets/origins/textures/particle/cosmetics/<id>.png`: the sprite sheet of each effect, texture string
  `origins:cosmetics/<id>`.
- `assets/origins/models/item/toolskin/<set>_<state>.json` + `assets/origins/textures/item/toolskin/<set>_<state>.png`:
  12 tool skin sets (catalog v1.2), 19 textures each: `sword`, `pickaxe`, `axe`, `shovel`, `hoe` (one design per tool
  type, shared by all 6 material tiers), `fishing_rod`, `fishing_rod_cast`, `bow`, `bow_pulling_0..2`,
  `crossbow_standby`, `crossbow_pulling_0..2`, `crossbow_arrow`, `crossbow_firework`, and for the modded tools
  `paxel` (Paxels, all 6 tiers) and `hammer` (one design shared by all 25 Just Hammers items, every kind and tier).

  `minecraft:item/handheld`, rod `handheld_rod`, bow states `minecraft:item/bow`, crossbow states
  `minecraft:item/crossbow` (so they keep the vanilla hand / third-person transforms).

- `assets/origins/models/cosmetic/<id>.json` + `assets/origins/textures/cosmetic/<id>.png`: hats (`hat_*`), back

  Model space in pixels: `(8, 0, 8)` = the neck, +y up, +z toward the back, +x toward the wearer's right (a Blockbench
  model facing north); head x 4..12, y 0..8, z 4..12; torso x 4..12, y -12..0, z 6..10. Every face gets its own texels
  (2 per pixel, 4 for the bandolier, medal, sash, amulet, bow tie and pendant) packed into the smallest square texture
  that holds them. Transparent texels
  (wing edges, flower corners) need a cutout render type on the client.
- `assets/minecraft/atlases/blocks.json`: adds the directory source `cosmetic` to the vanilla block atlas (atlas files
  from all packs are merged). Baked models only take sprites from that atlas; without it every hat renders as the

- `assets/origins/bedrock/poke_balls/variations/<ball>.json` + `assets/origins/textures/poke_balls/cosmetic/<skin>/

  variation per ball skin, keyed on aspect `origins_ball_<skin id>` (e.g. `origins_ball_ball_galaxy`); the client mod
  adds that aspect to the ball it draws. Model and poser are pinned to the ball's own base ones, the texture is drawn
  on that geometry's box UV (`poke_ball.geo`, 64x32, or `ancient_poke_ball.geo`, 64x32, with the ancient balls' extra
  plates, knob and wings).
- `cosmetics/cobblemon_balls.json` (not in the pack, committed): the ball list, each ball's base order / model / poser,
  the two geometries' texture size and box UV cubes, and the poser ids, read from the Cobblemon jar (name + SHA-1
  recorded). Regenerate after a Cobblemon update with
  `python -I cosmetics/build.py --refresh-cobblemon <path to Cobblemon-fabric-*.jar>`, then rebuild.
- `cosmetics/preview/` (not in the pack): `particles.png` every sheet at x8; `toolsets.png` the 12 sets x 19 textures
  at x6; `toolsets_x10.png` every set's sword / pickaxe / bow at x10 and at x2 on an inventory-slot grey;
  `toolsets_new_x10.png` the same for paxel / hammer, with the set's pickaxe for comparison;
  `wearables.png` every hat / back item rendered from the shipped model + texture (front, side from the wearer's
  right, back) on a grey head / torso at its contract position plus every ball skin texture at x4; `fronts.png` the
  same views for the front items. `tools_v1.png` is the frozen v1 tool preview, kept for comparison.

Ball variation precedence (Cobblemon 1.8.1, read from the jar's bytecode): `VaryingModelRepository.registerVariations`
lists every `bedrock/<type>/variations` folder (types include `poke_balls`), parses each file as a
`ModelVariationSet` (the ball id is the field `name`, JSON alternates `species` / `pokeball`), groups the sets by that
name, sorts each group with `sortedBy { it.order }` (stable, ascending) and concatenates their variations into one
`VaryingRenderableResolver`. `VaryingRenderableResolver.getVariationValue` walks that list from the end
(`listIterator(size)` / `previous()`) and takes, per field (model, poser, texture, layers), the first variation that
`fits` (all its aspects are in the ball's current aspects) and sets that field. So a set with a higher `order` wins;
Cobblemon's base sets are all `order` 0 with no aspects, ours are 100 and only fit when the skin aspect is present.
Model ids are `<namespace>:<geo file name without .json>` (`registerModels`: `File(path).nameWithoutExtension`); the
three posers the balls use (`cobblemon:poke_ball`, `cobblemon:beast_ball`, `cobblemon:ancient_poke_ball`) are
in-built, registered in code by `registerInBuiltPosers` via `inbuilt("<name>", ...)`.

Particle textures: Cobblemon 1.8.1 `SnowstormParticleReader.loadEffect` turns `basic_render_parameters.texture` into a
sprite id by dropping `.png`, removing every `particles/` and `textures/`, lowercasing and defaulting the namespace to
`cobblemon` (`ResourceLocationExtensionsKt.asIdentifierDefaultingNamespace`). `SnowstormParticle.getSpriteFromAtlas`
looks that id up in the vanilla particle atlas (`ParticleEngine.textureAtlas.getSprite`), and every Snowstorm material
renders from `textures/atlas/particles.png`. The vanilla atlas definition `assets/minecraft/atlases/particles.json`
stitches every PNG under `textures/particle/` of every namespace, so `origins:cosmetics/<id>` resolves to
`assets/origins/textures/particle/cosmetics/<id>.png` with no `particles/*.json` entry. A texture string must never
contain `particles/` or `textures/` inside its path.

`cosmetics/check.py` (also `python -I cosmetics/check.py [pack]`) fails the build on: invalid JSON anywhere in `pack/`,
a
particle identifier that does not match its path, a missing or wrongly sized particle texture (PNG size must equal the
UV `texture_width` x `texture_height`), an event spawning a missing effect, an override or parent pointing at a missing
model, a model texture that is missing or not a 16x16 PNG (cosmetic models: square 16..128), and non-binary alpha.
For tool sets: a set missing any of its 17 models / textures, a set model with the wrong parent, and any item x
`custom_model_data` x property combination (cast, pulling / pull around every vanilla threshold, charged, firework)
whose resolved texture is not the expected set state or the vanilla one. For front items: a missing model, or a corner
off the chest box (z above 6.5).
For hats / back items: a missing model for any id, a cube corner outside -16..32, a rotation not on one axis by
-45/-22.5/0/22.5/45, a face uv outside 0..16 or naming an undefined texture, and a texture not covered by a directory
source in the pack's `atlases/blocks.json`. For ball skins: a variation file for a ball Cobblemon does not ship, an
order not above Cobblemon's, a variation without an aspect (it would reskin the ball for everyone), a missing texture
or one not sized like its geometry, a model / poser id unknown to `cobblemon_balls.json` and the pack, and any skin x
ball pair without a variation. Vanilla resources the pack may
reference without shipping them are listed in `VANILLA_MODELS` / `VANILLA_TEXTURES` there.

## Cosmetic icons

Every cosmetic has its own menu icon (wardrobe, `/store`, crate previews): the item string
`minecraft:knowledge_book[custom_model_data=<n>]` in the cosmetic's `icon`, drawn by this pack. Players never hold a
knowledge book, and paper stays reserved for the menus. Generated by `cosmetics/icons.py` (called at the end of
`cosmetics/build.py`), do not edit by hand:

- `assets/origins/models/item/icon/<id>.json`: aura, trail, sendout, victory, nickname, emote and ball skin icons are
  `minecraft:item/generated` with a 16x16 texture `assets/origins/textures/item/icon/<id>.png`; tool skins use the
  set's pickaxe model (`origins:item/toolskin/<set>_pickaxe`, set from the cosmetic's `custom_model_data`); hats,
  back and front items use the wearable model itself (`origins:cosmetic/<id>`) with a `display.gui` whose rotation
  is fixed per kind and whose scale / translation are computed so the model fills the slot without leaving it.
  `plain_knowledge_book.json` is a copy of the vanilla look.
- `assets/minecraft/models/item/knowledge_book.json`: the vanilla parent and texture, one override per icon in
  ascending `custom_model_data`, then `<last + 1>` -> `origins:item/icon/plain_knowledge_book`. Overrides are tested
  last to first with "value >= threshold", so each number shows its own icon and anything above the range is a plain
  knowledge book again.
- `cosmetics/preview/icons.png`: every icon at x4 in a dark menu slot, grouped by type and labelled (wearables
  rendered from the shipped model with their `display.gui`); `icons_1x.png`: every icon at real size on dark menu
  slots (left) and vanilla grey slots (right), x2 nearest (wearables rendered at 32 px, what GUI scale 2 draws).

Art (all original, one texel per icon pixel, light from the top-left, binary alpha, deterministic, an INK outline
round every flat icon, a lighter RIM next to near-black art). Aura, trail, sendout, victory and nickname icons are
hand-drawn 16x16 templates (16 strings of 16 characters, each character a palette role), one file per type:
`cosmetics/icon_art_aura.py`, `icon_art_trail.py`, `icon_art_burst.py` (sendouts), `icon_art_victory.py` and
`icon_art_nick.py`; `icon_art_base.py` holds what they share (`drawn()`, which adds the outline, `relabel()`,
`rainbow()` and the shared emote palettes) and `icon_art.py` merges their `ICONS` and states the drawing rules. An
icon shows the real effect: its own particle sprites (`cosmetics/build.py` EFFECTS / PARTS, `art_fx2.py` EFFECTS2 /
PARTS2) in its own palette, laid out the way they move in game; auras and sendouts show the effect alone (no wearer,
ring or ball), trails a path receding from bottom-left to top-right, victories the hero sprite large in the centre.
Ball skins are a lit sphere sampled from the skin's own art; emotes the emote sprite from `src/emotes/` (credits
there); hats, back and front items the model itself, framed per kind (`GUI_VIEW`) or per item (`GUI_OVERRIDE` in
`cosmetics/icons.py`, only `display.gui` changes).

To give a new aura / trail / sendout / victory / nickname its icon: refresh the catalog (below), draw its template in
its type's file (copy a neighbour: template, a comment naming the sprites and palette, an entry in that file's
`ICONS`), then `python -I build.py`. The build fails until every such id has a template. Check the result in
`cosmetics/preview/icons.png` and `icons_1x.png` on both slot colours.

Numbering lives in `cosmetics/icons.json` (`{"<id>": {"cmd": n, "type": t}}`, committed) and is append-only: a number
is never changed or reused, because the live configs point at it. A cosmetic removed from the catalog keeps its entry
and its icon. `cosmetics/icon_catalog.json` (committed) is the snapshot of the catalog fields the art needs (type,
name, rarity, colors, effect, custom_model_data). After the cosmetics catalog changes, refresh both from the config
the server runs, then rebuild:

    python -I cosmetics/icons.py --refresh-catalog <path to cosmetics.jsonc>
    python -I build.py

New ids get the next numbers in catalog order; then point their `icon` at them in the configs
(`packdev/server/tools/cosmetic_icons_patch.py`). Until then a new cosmetic keeps its plain item icon.
`cosmetics/check.py` fails the build on an id without a number, numbers that are not unique and contiguous from
7500001, a missing icon model or texture, a wrong icon parent, knowledge book overrides out of order or without the
catch-all, a hand-drawn template whose id is not in `icons.json`, an aura / trail / sendout / victory icon whose art
is under 12 px in its larger dimension, and two icons of one of those types whose opaque masks differ by fewer than 24
pixels (same layout, they would read alike in a store list).

## Animated nicknames

Gradient nickname styles flow along the name and loop every 3 s. The server mod writes each char of a gradient nickname
in a marker colour (`origins_cosmetics` `AppliedLogic.nickMarkers`); the text vertex shaders here recognise it and draw
the style's colours instead. Spec: `packdev/server/specs/origins-cosmetics/animated-nicks.md`.

- `assets/minecraft/shaders/core/rendertype_text{,_see_through,_intensity,_intensity_see_through}.vsh` + `.json`:
  vanilla 1.21.1 plus one call to `nick_vertex` and the `GameTime` uniform. No `.fsh` on purpose: the modpack's
  "Cobblemon Origins UI" pack (Paxi, loaded above this one) ships its own `rendertype_text.fsh`, so all the work is per
  vertex and any fragment shader keeps working.
- `assets/minecraft/shaders/include/origins_nick.glsl`: generated by `nicks.py` from the gradient nickname styles in
  `cosmetics/icon_catalog.json` (`colors` and the optional `marker`), do not edit. Loop length, spread and the decode
  live there (settings at the top of `nicks.py`).
- `nicks.check` (run by `build.py`) proves every marker and marker shadow decodes to itself and that no real text colour
  or its shadow decodes as a marker: vanilla colours, catalog colours, the old static gradients, the menus here and
  `nick_scan.json`. Refresh that snapshot after adding a gradient nickname or a coloured config, from `packdev`:
  `python -I server/resourcepack-icons/nicks.py --scan server mods ../config`. On a collision it prints the nearest free
  cell; put it in the style's `"marker": "#RGB"` in cosmetics.jsonc, refresh the catalog, rebuild, and ship the server
  config together with the pack.
